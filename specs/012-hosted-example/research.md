## R1 The output contract with the infrastructure owner

- Two owners, two repositories, no shared state: the infrastructure owner composes the project, bootstrap, billing, APIs, IAM and state and publishes a versioned output contract; this repository consumes it as typed inputs (`deploy/gcp/inputs/contract.schema.json`: project id, region, runtime identity, build identity, state bucket, artifact registry, contract version). A missing or newer-than-supported contract version is refused by validation. The contract is published as `deploy/gcp/inputs/contract.schema.json` (version 1, the seven fields), referenced by the inputs schema rather than restated, and `TestTheContractSchemaIsTheOneTheFunnelConsumes` keeps it equal to what the funnel consumes. The agreed task ids on the infrastructure side are recorded here when settled; until then T002 stays open on that half.

## R2 Issuer and verification library (probe at T003)

- The server's `identity.Verifier` takes a bearer token and returns an opaque subject; production composes it through `newVerifier`, which is nil today, so production refuses to start, and that refusal is what spec 009's image witnesses. The probe chooses a supported token issuer and a maintained verification library for it, pins the library by go.sum after the probe, and writes the negative tests with synthetic keys: wrong issuer, wrong audience, expired, bad signature. The development identity is never composed into the production binary (`//bff/cmd:binaries_test`).
- Probed and landed at T003 and T007: the issuer is any provider that signs JSON Web Tokens and publishes its keys as a JSON Web Key Set (what OpenID Connect providers do); the library is `github.com/golang-jwt/jwt/v5` 5.3.1 (MIT) for parsing and validation with `github.com/MicahParks/keyfunc/v3` 3.9.1 (Apache-2.0; `jwkset` and `x/time` beneath it) for the key set, fetched once at start and refreshed for the life of the process, chosen over `go-oidc` for a smaller dependency tree (no OAuth client). `bff/adapters/identity/oidc` implements `identity.Verifier`: asymmetric algorithms only, issuer, audience and expiry required, thirty seconds of leeway, the subject returned, and every rejection `ErrUnauthenticated` with no reason; the tests use synthetic RSA and P-256 keys served by a local key set and refuse a wrong issuer, a wrong audience, an expired token, a token issued in the future, a bad signature, an unknown key, a missing subject, a symmetric or `none` algorithm, and a key of the other kind; a start with an unreadable or empty key set fails, which the first test run caught because the client logs a failed fetch and continues. The production composition names the issuer through three inputs with no default and refuses to start without them, the refusal spec 009's image witnesses with its new exact text.
- Landed at T010, the page's side: the production page signs in through the authorization code flow with a proof key (PKCE, RFC 7636) against the issuer `config.json` names, as the client whose id is the verifier's audience, so the issuer and the audience stay declared once (FR-003). No sign-in library: the flow is the discovery document, a redirect and one token request, written in `web/app/signin/oidc.ts` behind ports a test supplies, and measured at 100 percent (`ts-signin`). The identity token is the bearer credential; the page keeps a token only when it says it is from the issuer, for the client, for the sign-in this tab started (state and nonce), and the server does the verification that counts. The session lives in the tab's storage until the token's expiry; sign-out forgets it and does not end the issuer's session. The issuer's endpoints must be https, or http on a loopback address, as the server's key-set URL must. The journey against a local issuer landed at T014 (`web/e2e/issuer.mjs`, `signin.spec.mjs`): the production bundle, the production server with its verifier pointed at the local key set, the sign-in through the issuer's page, and the server refusing the development identity, another audience and a tampered signature; a real issuer is T017's.

## R3 Store (probe at T004 and T019)

- Probed and landed at T004 and T008: the simplest managed store with owner-scoped keys is an object bucket, one object per note under `notes/<hex owner>/<hex id>.json`, written and read through two calls of the bucket service's JSON API with a token the runtime reads from its own metadata endpoint; no client library, so nothing new is pinned. Firestore was the alternative and needs a client library with a large dependency tree for two operations. `bff/adapters/store/object` passes the same contract suite as the memory fake and the file-backed store, with a read after a restart and owner isolation, against a fake of exactly those two calls and the token endpoint, which stands for the API surface and not for the service: the live bucket is a gate (T017). Every failure is unavailable, never an empty note; the token is cached until shortly before it expires; names never leave the prefix. The bucket is the infrastructure owner's (`contract.notes_bucket`), and the runtime identity's permission to create and read objects in it is enumerated on the owner's side.
- `ports.Store` has `Put` and `Get` by owner and id with `ErrNotFound` and `ErrUnavailable`; the memory adapter is bounded. The local demo takes a file-backed adapter under the same contract suite with stated persistence, restart and reset semantics; the hosted example takes the simplest managed store with owner-scoped keys, under the same suite, with a read-after-restart test and an owner-isolation test. A one-instance limit is never a durability claim.

The binary's drain and telemetry shutdown bounds are 5 seconds each, in turn, so the worst case uses the whole window, and exports from an idle instance can wait for the next request. Conclusion for the plan: Cloud Run fits the server's contract once the three application gaps (verifier, store,
`PORT`) are closed by the adapters the spec already requires; nothing about the service weakens the server's
refusals or its exact origin. The decision stays provisional until the adapters exist and an authorized live run
records the endpoint, the identity, the digest and the flow.

## R5 Pages base path and the browser origin (probe at T006)

- Recorded at T006 from the local hosted journey (`//web/e2e:hosted_e2e_test`): the page under a project-site path reads its script and its configuration relative to the path and nothing at the root, the backend's allowed origin is the host alone, and the preflight passes for it; the live Pages site itself has not been served, which is T017's. A Pages project site serves under a path while the browser origin is the host alone; CORS here allows one exact origin with no path, and that stays. The frontend base path and the RPC base URL are independent inputs; the journey tests the preflight, a blocked foreign origin, an authenticated call, error and status accessibility, reload and deep link, logout and cancellation, and log redaction.

## R6 The local launcher on a host with bash 3.2 (independent Mac probe, 2026-11-01)

- An independent probe on macOS ARM at `34e1bbc` found `/bin/bash` 3.2.57, which refuses `wait -n`, the call the launcher ended with; no GNU `timeout` or `flock` on PATH either. The launcher now needs bash 3.2 and POSIX tools only: the first child's exit is detected by a `kill -0` poll with the same semantics, both children are stopped by the same trap, and a busy or invalid port is refused by name before anything starts, through bash's own `/dev/tcp` connect. The demo's host requirements are stated apart from the full verifier's. Native macOS is recorded only from an independent native run; Linux end-to-end coverage proves nothing about it.
