# Evidence: M5 quality registry, runner and hooks

This records what has been observed for M5, and what has not. A claim holds only for the revision and
isolation label beside it. The one independent result here is named as such, and it predates the last repair.

## Order of work

The source history is the record of what came first.

- Plan, tasks and matrix came before production adapter code, after scratch probes recorded in research.
- The runner was written before its executable unit tests. It was not test-first, and no red-before-code
  claim is made for it.
- Review counterexamples were reproduced red first, then repaired. A draft run showed three false greens
  and a hung `--path` case that timed out. That timeout stopped the identity and closed-enum cases from
  running at all, so those were qualified afterward with valid mutants.
- The receipt repair was red first: with the real runner holding its lock, starting the wrapper deleted
  the sentinel receipt.
- The spent-context fix was red first, through its unit test. The run-level test beside it passed on the
  unfixed code, so it pins the missing-evidence result and proves nothing about the fix.

### Results that were not credited

- `runInner` given the checkout as its directory survived, and the mutant was invalid: the script is
  bound to the worktree when it is built. It was retargeted to the build directory.
- That retarget still left the push fixture able to pass, for a real reason: prek stashes unstaged changes
  at pre-push too, which put the defect back in the checkout. The fixture now stages the fix.
- The first custody batch never reached its custody sections. `new_repo` skipped `git init` when any
  parent directory was a repository, and the mutant copies sat inside one. That batch's results are
  invalid, and its scratch logs were overwritten by the next batch. The batch's task output kept their tails.
- A shared-server mutant that ran `bazel shutdown` hung the copied tree's own `runner_test` in section 2,
  twice, ending in `exit 124`. That is a setup failure. It was replaced by the mutant in the table.
- The first receipt-mutant batch copied the wrong runner path. Its baseline failed, so all of it is
  void. In the rerun, the first `flock` check mutant made the error always fire and failed the first
  control instead. It was rebuilt to remove the check.
- An untracked `MODULE.bazel` in the quality module did not break the runner, so it was no bootstrap
  control. The control now uses an empty untracked `tools/checks/BUILD.bazel`.

## Measurement

The record is `docs/budgets/linux-x86_64-20c-stages.json`, measured at `7366549`, tree `bf608ea`, on a
shared 20-CPU, 62 GB Ubuntu 24.04 x86_64 host at a load average of 14 to 30, labeled `weakened`. Install
and first runs have n=2, so their p95 is the slower of two samples and sets no cold contract. Each warm
scenario has n=10, so its p95 is close to the worst sample. Times cover a whole `git commit` or `git push`,
including prek.

The last column of the table counts `test.xml` files whose path or modification time the push changed in
the private output base. This is a proxy. It is not a cache-aware record of test execution, and a rewritten
result file alone does not prove a fresh run.

| Scenario | p50 s | p95 s | Spawned actions | `test.xml` updates |
| --- | --- | --- | --- | --- |
| Hook install, empty `HOME` | 13.5 | 14.1 | | |
| First commit after install | 42.0 | 50.7 | | |
| First push after install | 69.0 | 86.6 | | |
| Pre-commit, 1 staged file | 0.8 | 0.9 | | not a test stage |
| Pre-commit, 50 | 0.8 | 0.9 | | not a test stage |
| Pre-commit, 500 | 0.8 | 0.8 | | not a test stage |
| Pre-commit, rejected | 0.8 | 1.1 | | not a test stage |
| Pre-push, comment edit | 1.2 | 1.8 | 7 | **0** |
| Pre-push, exported constant | 1.7 | 1.9 | 41 | **0** |
| Pre-push, new `init` function each sample | 2.0 | 2.1 | 51 | 8 per sample: the package's and 7 dependents', in 10 of 10 samples |
| Pre-push, failing test | 1.2 | 1.3 | 8 to 9 | 1 per sample, the package's, in 10 of 10 samples |
| Pre-push, documentation only | 1.0 | 1.2 | 0 to 8 | 0, except 1 of the package's in one sample |

The provisional warm targets are hypotheses of 5 s for pre-commit and 90 s for pre-push, for an 8 vCPU, 32 GB
profile. These results are below both numbers, but this host is larger and its isolation is weakened, so
they do not qualify that profile.

**What these numbers do not show.** The comment and exported-constant rows updated no `test.xml`, so they
are compile and cache times, and they are not feedback on behavior. Only the `init` row is a passing edit
with test results updated: each sample adds a new retained `init` function, and the result is scoped to that
edit of one package and its dependents. Not every documentation sample was answered by the cache alone:
the first followed the restoration from the failing-test scenario, and it shows one update of the package's
own result.

Peak memory in this record is 2.4 to 3.1 GB warm and 3.9 GB on a first push. It counts both Bazel servers,
idle or not, so it is the envelope of having hooks in use, not the cost of one stage. It is sampled every
0.1 s and can miss a short spike. It is an observation, not a limit this template promises.

**Superseded records.** Two earlier records are not evidence and were not committed. At `042c6f5`, memory
dropped the servers, and the scenario was called a retest with nothing to show it. At `58d0edf`, memory had
the same fault and no passing scenario updated a test result. The older
`docs/budgets/linux-x86_64-20c.json` keeps its raw figures for its own revision, with a qualification beside
them: its sampler joined newline-free pid files, so its peak memory is unreliable wherever two servers were
alive, and no figure in it is a memory promise. Its revision also predates `hook-e2e`, so the current
full run costs more than it says.

The record stays attributed to `7366549`. Later changes did not touch the staged or runtime scenarios or the
tools they measured, so it was not repeated.
