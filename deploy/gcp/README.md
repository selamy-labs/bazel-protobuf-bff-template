# Hosted example on GCP

The template's own hosted example (spec 012): the synthetic application deployed by Cloud Build into a dedicated,
BFF-owned project from the exact image spec 009 builds, by digest, with the static frontend on GitHub Pages.
Nothing here is applied by this repository; every create, apply, access, billing and spend step is a recorded
operator gate, and no resource exists yet. Nothing in the pipeline has ever run live in GCP Cloud Build:
the step logic, plan storage roundtrip, and approval verification are witnessed offline
in `deploy/gcp/tests/offline.sh`; the offline harness checks only their text, and live
Cloud Build template substitution remains unverified until a live run. The reusable core stays portable: none of this is required to use the
template.

| Path                         | What it holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inputs/`                    | the one typed funnel: `inputs.schema.json`, `contract.schema.json` (the infrastructure owner's output contract, which the inputs schema references), a synthetic `example.inputs.json`, and the validator every plan runs first (the contract now names `notes_bucket`, the managed store's bucket): `validate [--overlay <file>]... [--effective <path>] <inputs file>` merges the base file and an operator's overlays leaf by leaf (the last file wins), refuses a leaf no file gives, prints each effective value with the file that gave it, and writes the effective document the plan reads. Real inputs, state, plans and evidence stay outside the repository |
| `service/`                   | one Cloud Run service serving the release's digest from the contract's registry as the contract's runtime identity, with the funnel's port, origin, verifier settings and bounds, and the public invoker binding; the provider is pinned by checksum and bound to the funnel's project and region; `tests/service.tftest.hcl` are its mock tests                                                                                                                                                                                                                                                                                                                       |
| `cloudbuild/cloudbuild.yaml` | the deployment pipeline: validate the inputs, promote the exact image by digest into the contract's registry (nothing is built), plan mode when `_APPROVED_PLAN_SHA256` is empty to generate and store the reviewed plan and digest, apply mode when `_APPROVED_PLAN_SHA256` is supplied to verify the stored plan before apply behind the operator's approval gate, record the digests before and after. The trigger, its connection to the public repository through the organization's existing Cloud Build application, the tools image it runs and its approval setting are inputs the infrastructure owner and the operator provide; none is declared here                                                                                                  |
| `tests/offline.sh`           | the witness `//deploy/gcp:offline_test` runs: the inputs validated first, then format, validate, the declared resource graph of exactly two resources, the provider bound to the funnel, and the mock tests, from a mirror of the pinned provider with no network and no credentials; seventy planted defects fail                                                                                                                                                                                                                                                                                                                                                           |

The service passes the production binary its telemetry inputs from the funnel: `runtime.telemetry.endpoint`,
`.environment` and `.sample_ratio`, and the revision of the digest it serves, which is `image.source_revision` or,
in a rollback, `release.previous_revision`. The binary refuses to start without an endpoint and a revision, so these
are required here too. The endpoint is an https origin the service exports to without credentials: no collector is
declared in this module, and `docs/quality/telemetry.md` lists what a hosted run must decide first. The funnel
refuses an origin the service could not reach: a loopback, unspecified, link-local, multicast, private or zoned host,
or one not spelled in ASCII, which a transport would map to something else before it dials.

The infrastructure owner composes the project, bootstrap, billing, APIs, IAM and state in its own repository and
publishes a versioned output contract; `inputs.schema.json` names the fields this repository consumes from it.
No state is read across that boundary.
